## 3안 세부 평가

### 최소안 — MacBook Pro 14" / M4 Pro 12코어 / 48GB / 512GB

**왜 48GB인가:**
Legend Nexus 에이전트 시스템은 서브에이전트를 병렬 구동한다. Claude Code 프로세스 자체가 상당한 메모리를 점유하고, Arki가 제시한 64GB 기준은 멀티에이전트 병렬 실행 + OS + 브라우저 동시 구동을 전제한다. 48GB는 **에이전트 3~4개 병렬 + 경량 브라우저 단일 탭** 정도에서 한계를 보인다. 3년 차 접근 시 macOS 메모리 압박(swap 전환) 가능성이 있다.

**SSD 512GB 위험:**
파일 기반 JSON/Markdown + git 히스토리(세션당 수십 KB, 200세션 이상 축적) + Claude Code cache + macOS 시스템 = 실사용 잔여 공간이 빠르게 줄어든다. 2년 차에 여유가 사라질 가능성 있음.

**3년 관점:** RAM이 먼저 한계에 도달한다. 14"는 폼팩터 제약도 있어 방열 여유가 16"보다 낮다 — 지속 고부하 시 쓰로틀링 빈도 차이 발생 가능 (추측, 실측 아님).

**판정: 예산 제약이 없다면 비추천.** 3년 기준 ROI가 떨어진다.

---

### 적정안 — MacBook Pro 16" / M4 Pro 14코어 / 64GB / 1TB ← **권장**

**왜 이 조합인가:**
- Arki 메모리 기준(64GB) 충족
- 16" 방열 여유 → 지속 고부하(에이전트 병렬 실행)에서 M4 Pro 풀 퍼포먼스 유지 가능성 높음
- 14코어 CPU = 12코어 대비 CPU-bound 스크립트(hook chain, ts-node 컴파일, git 연산) 처리 차이 발생 (추측: 체감 15~20% 차이)
- 1TB SSD: git 히스토리 + session 아카이브 + 개발 환경 여유 충분
- M4 Max 대비 **약 280만원 절감** — 이 차액이 실질 성능 차이를 정당화하는가?

**3년 관점:** RAM 여유가 충분하다. 병렬 에이전트 수를 늘려도 5개 이상에서도 swap 없이 처리 가능할 것(추측). 단일 한계 지점이 3년 내에 오지 않는다.

**판정: ROI 최대. 이 라인업의 최적점.**

---

### 최상안 — MacBook Pro 16" / M4 Max 16코어 / 128GB / 2TB

**M4 Max가 의미 있는 조건:**
M4 Max의 진짜 차별점은 **GPU 코어(40코어)와 Unified Memory 대역폭(546GB/s vs Pro 273GB/s)**이다. 이는:
- 로컬 LLM 추론(Ollama 등)을 병렬로 돌릴 계획이 있을 때
- 영상 편집·렌더링이 병행될 때
- 128GB RAM을 실제로 채울 워크로드가 있을 때

**Legend Nexus 워크로드 관점:**
Claude Code는 API 기반 → 로컬 GPU 불필요. hook chain은 Node.js/ts-node → CPU 단일 스레드 병목. 에이전트 병렬 실행은 RAM 의존이지 GPU 대역폭 의존이 아니다. **128GB → 64GB 대비 실사용 차이는 워크로드 특성상 미미할 가능성이 높다.**

**과투자 경고:**
M4 Max(128GB) 선택 시 추가 지출 약 280만원. 이 280만원이 Legend Nexus 시스템 성능 개선으로 회수되는 경로가 현재 워크로드에서 명확하지 않다. GPU 대역폭, 128GB RAM은 현재 요구 사양을 크게 초과한다.

**판정: Legend Nexus 전용 기계라면 과투자. 단, 로컬 LLM 실험이나 다른 고강도 워크로드가 병행될 계획이 있다면 정당화 가능.**

### MacBook Pro 14" vs 16" — 폼팩터 실질 차이

| 축 | 14" | 16" |
|---|---|---|
| 방열 설계 | 팬 소형, 지속 고부하 시 쓰로틀링 가능 | 팬 대형, 방열 여유 더 큼 |
| 무게 | ≈ 1.61kg | ≈ 2.14kg — 둘 다 ≤2.5kg 기준 충족 |
| 화면 | 14.2" | 16.2" — 멀티에이전트 모니터링 시 실사용 차이 있음 |
| 비용 | 더 저렴 | 적정안 기준 +30~50만원 |

**판정:** Legend Nexus 워크로드(지속 고부하)에서 16"가 유리. 무게 기준 둘 다 충족이므로, **16" 우선**.

### M4 Pro vs M4 Max — 에이전트 시스템 실질 차이

| 축 | M4 Pro (14코어) | M4 Max (16코어) |
|---|---|---|
| CPU | 14코어 | 16코어 (+약 14%) |
| Unified Memory 대역폭 | 273 GB/s | 546 GB/s (×2) |
| 최대 RAM | 64GB | 128GB |
| GPU | 20코어 | 40코어 |
| 적합 워크로드 | API 기반 에이전트, 코드 빌드, 스크립트 | 로컬 LLM, 영상, 렌더링 |

**Legend Nexus에서 M4 Max 대역폭이 의미 없는 이유:** 에이전트 병렬 실행은 메모리 용량이 병목이지, 대역폭이 병목이 아니다. hook chain(ts-node), git 연산, JSON 파일 I/O는 CPU 단일 스레드 성능이 결정 요인이다.

**판단: 64GB 충족 시 M4 Pro로 충분. M4 Max 추가 비용은 현재 워크로드에서 회수 경로가 불명확.**

---

### SSD 용량 — 최소 필요량

현재 프로젝트 구조 기준:
- `topics/` + `memory/` + `reports/` + `app/` + `scripts/` ≈ 추정 수백 MB (현재)
- 세션 누적(~200+ 세션, 계속 증가) + git 히스토리 = 연간 약 2~5GB 증가 예상 (추측)
- Node.js 환경 + TypeScript 빌드 캐시 + macOS 시스템 = 100GB 이상 상시 점유

**결론:** 512GB는 2년 차에 압박 가능. **1TB 최소 권장.** 용량 부족은 추후 외장 드라이브로 보완 가능하지만 마찰이 생긴다.

## Riki 리스크와 비용 연계

Riki가 R-2·R-3에서 제기한 `shell:false` 무음 실패는 macOS 전환 **직후** 핵심 리스크다. 이것은 하드웨어 선택과 독립적으로 **반드시 선처리**가 필요한 소프트 비용이다.

**마이그레이션 비용 구조:**
- hook 패치(R-2) + cwdToProjectDirName 검증(R-1) + `__dirname` 정리(R-4): 개발 공수 집중 구간. 하드웨어 전환 후 첫 세션에서 진단 세션을 별도로 잡지 않으면 **2~3세션 분의 session_contributions 누락 가능**.
- 이 누락은 역할들의 컨텍스트 품질 저하로 이어진다 — 비재무 손실이지만 실질 생산성 비용.

**권고:** macOS 전환 전에 hook 패치 토픽(별도 Grade C)을 먼저 닫는 것이 비용 최소화 경로다.
