# Ace — Debate Round 2: Grade 재정의

## Q1. Master 제안(C 재정의)과 Ace Round 1 판정(C 폐기) — 구조적 차이인가, 레이블 차이인가

**레이블 차이가 아니다. 구조적으로 중요한 차이다 — 그리고 Master 제안이 옳다.**

Ace Round 1 판정은 "C를 폐기하고 그 자리를 B 격상이 대신한다"였다. 이 구조의 문제는 격상 판단을 Nexus에 완전 위임한다는 것이다. "Arki 필요하면 B로 올린다"는 B와 D 사이의 중간 처리 경로를 없애고 Nexus 판단력에 의존하는 구조다.

Master 제안("C를 재정의 — Dev 고정 아닌 경량 처리 + 필요 역할 호출")은 다르다. **C라는 슬롯을 유지하되 첫 주자·역할 고정을 없애고, 경량이지만 구조적 판단이 필요한 공간을 명시 보존**한다. 이것이 Round 1 Arki 입장("C 유지 + Dev-pull 전환")과 정합하며, Riki의 핵심 우려("C/D 통합 시 구조 결함 누적 위험")를 그대로 해결한다.

**Ace 입장 전환**: C 폐기 → C 재정의 수용. 근거: "C를 폐기하고 Nexus가 B로 격상"은 이론상 같아 보이지만, 실운용에서 B 격상 트리거가 없으면 그냥 D로 처리된다. C 슬롯이 있으면 Nexus가 "이건 D냐 C냐"를 명시 판단하는 게이트가 존재한다. 슬롯 존재 자체가 판단 강제다.

## Q2. 새 C의 역할 구성 원칙 — Nexus 자동 판단 가능 형태로 구조화

**"경량 처리 + 필요 역할 호출"을 Nexus가 판단 가능하게 만들려면 역할 호출 조건이 인풋 신호로 박제되어야 한다.**

현재 C의 문제는 "Dev→Arki 검토→Dev 수정"이라는 순서를 고정했는데 Arki 호출이 실제로 거의 발생하지 않는다는 것이다. 이것은 순서 고정 자체가 문제가 아니라 **호출 조건이 불명확**하기 때문이다. "필요 시"는 판단 기준이 없다.

새 C의 역할 호출 조건:

| 신호 | 호출 역할 | 판단 근거 |
|---|---|---|
| 기존 파일 2개 이상 동시 수정 | Arki | 의존 관계 검토 필요 |
| 신규 인터페이스·API 표면 변경 | Arki | 구조 파급 범위 있음 |
| 비용·자원 조정 포함 | Fin | cost-eval 신호 |
| 실패 가능성 명시 ("테스트 없음", "레거시 건드림") | Riki | risk-audit 신호 |
| 위 신호 없음 | Dev 단독 | 순수 경량 실행 |

이 5줄이 Nexus가 C 토픽에서 체크하는 인풋 신호 목록이다. "필요 역할 호출"을 LLM 자유 판단이 아니라 **신호 매칭으로 박제**해야 Nexus 자동 판단이 가능하다.

첫 주자: Dev 고정 해제. 첫 발언자는 신호 목록 기반으로 결정. 신호 없음 = Dev 직행. Arki 신호 있음 = Arki→Dev. Fin 신호 있음 = Fin→Dev. **C에서 Arki/Fin/Riki는 Dev 이전에 선제 호출, Dev 이후 확인 호출이 아니다** — 이게 이전 C의 운용 실패 원인이었다.

## Q3. B vs 새 C 경계 — 단일 기준

**기준: 결정 파급 범위가 역할 로스터 구성 전 판단 가능한가 여부.**

3가지 후보 기준 기각:

- **파일 수**: B가 6~10, C가 ≤5 — 숫자 임계가 자의적이고 미래 코드베이스 크기에 따라 의미가 달라진다. 기각.
- **2축 적용 여부**: "C는 2축 미적용"은 설명이지 기준이 아니다. 2축을 적용할 수 없어서 C인가, C이기 때문에 2축 불필요한가 — 순환이다. 기각.
- **결정 파급 범위**: 단일 모듈·파일 내 완결 vs 모듈 경계를 넘거나 다른 역할의 설계 인풋이 됨. 이것이 호출 시점에 Master 발화에서 판단 가능한 유일한 기준이다. **채택.**

**B vs C 경계 단일 기준:**

> "이 토픽의 실행 결과가 다른 시스템·역할·결정의 인풋이 되는가?"

- Yes → B (Arki 선두, 구조적 검토 필수)
- No → C (신호 기반 선택 호출, Dev 중심)

보조 판별: 파일 수는 2차 신호. 파일 5개 이하여도 "인증 미들웨어 전면 교체"는 B다. 파일 10개여도 "스타일 시스템 10개 파일 일괄 rename"은 C다. **파급 범위가 1차, 파일 수는 보조.**

## Q4. Grade 5단계 전체 재정의안

**원칙 단일화: Grade = 결정 파급 범위 × 불확실성 수준 × 2축 적용 여부.**

| Grade | 정의 | 불확실성 | 파급 범위 | 2축 | 첫 주자 | 역할 구성 |
|---|---|---|---|---|---|---|
| **S** | 오픈 탐색형. 문제 정의 자체가 Master 결정 필요 | 높음(open) | 조직·전략 전체 | full | Master 선언 → Jobs(`/jobs-framing` 시) → Ace | Jobs→Ace→Arki·Riki→Fin→Edi / Nova·Vera 선택 |
| **A** | 닫힌 실행형. 구조 설계 결과가 다수 역할·시스템 인풋 | 중간 | 시스템 경계 횡단 | full | Arki | Arki→Fin→Riki→Ace(`/ace-synthesis` 시)→Dev→Edi / Nova·Vera 선택 |
| **B** | 명확 결정건. 실행 결과가 다른 결정·시스템 인풋이 됨 | 낮음~중간 | 모듈 경계 횡단 | 2축 판별 적용 | Arki | Arki→Riki→Ace(`/ace-synthesis` 시)→Dev→Edi |
| **C** | 경량 처리. 실행 결과가 단일 모듈 내 완결 | 낮음 | 단일 모듈 내 | 신호 매칭 | 신호 기반 (Dev 기본) | Dev 기본 / Arki·Fin·Riki 신호 조건부 선제 호출 |
| **D** | 명백 단순 작업. D 키워드 또는 완전 자명 | 거의 없음 | 로컬 | 없음 | Dev 직행 | Dev→Edi 생략 가능 |

**2축과 Grade의 연동 방식:**

2축(closed/open × decision/execution)은 S/A/B에서 첫 주자와 역할 구성을 정밀화하는 역할이다. C/D에서는 파급 범위가 이미 좁으므로 2축 불필요.

```
Grade 판정 우선
  → C/D이면 2축 미적용, 신호 매칭
  → B이면 2축 적용 → 패턴 매칭 → 역할 구성 확정
  → A/S이면 2축 적용 → 첫 주자 결정 → subjectType 태그
```

**D 정의 변경 없음**: 현행 D("≤5, 명백 단순, Dev 직행") 유지. 현재 C의 "판단 여지 없는 경량 작업"이 D로 흡수. D에서 "파일 2개 이상 동시 수정" 신호 감지 시 C로 격상 — 이 트리거를 D 정의에 인라인 박제.

## Q5. S 로스터 최종 확정

**확정안: Jobs→Ace→Arki·Riki→Fin→Edi, Nova·Vera 선택.**

이 구조가 맞다. 2개 박제 필요:

**박제 1: Jobs 발동 조건 인라인**
```
S grade에서 Jobs는 `/jobs-framing` 명시 호출 시만 framing phase 진입.
자동 트리거 0. 명시 호출 없으면 Ace가 구조 판정 선두.
```

**박제 2: S 선언 제한**
```
S = Master 명시 선언 전용.
Ace는 "S 승격 검토 권고" 후 Master 승인.
Nexus 자동 S 판정 금지.
```

Nova·Vera 선택 유지: S 토픽 탐색형 + Nova 추가 시각 구조 = 선택 포함 맞음. Vera는 UI/디자인 산출물 있는 S 토픽에서만 의미 있으므로 선택 유지.
