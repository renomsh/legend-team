# Jobs — Debate Round 2: Grade 재정의

---

## 1. "새 C = 경량 + 필요 역할 호출"이 현행 B와 어떻게 다른가

**결론: Size만 다르고 구조는 동일하다. 그렇다면 구분은 의미 없다.**

Master 제안의 "새 C"는 본질적으로 B의 축소판이다:

| 항목 | B | 새 C (Master 제안) |
|---|---|---|
| 역할 구성 | 필요 역할 호출 (Arki 선두 default) | 필요 역할 호출 (선두 미정) |
| Size | 6~10 파일 | ≤5 파일 |
| 결정 여지 | 있음 | 있음 |
| Dev 고정 | 없음 | 없음 (현행 C에서 변경) |

"필요 역할 호출"이라는 기준은 B와 동일하다. 유일한 차이는 Size다. 이 경우 Nexus는 토픽을 보고 두 번 판단해야 한다: ①역할 구성 결정 + ②Size 레이블 부여. 그런데 역할 구성이 이미 결정되면 Size 레이블은 무엇을 위한 것인가?

**더 큰 문제: "필요 역할 호출"은 판단 기준이 아니다.** 이것은 결과 기술이지 입력 기준이 아니다. "어떤 역할이 필요한가"를 판단하는 기준이 외재화되지 않으면, 새 C 정의는 "Nexus가 알아서 판단하라"와 동일하다.

**Jobs 결론:** 새 C = B (Size만 작음). 이를 별도 Grade로 유지하는 이유가 없다. Size 차이는 Grade 레이블보다 토픽별 역할 호출 판단에서 자연스럽게 처리된다.

## 2. "C → D 편입 + 새 C 정의" vs "C/D 통합 + B 격상 트리거" — 어느 쪽이 더 명확한 의사결정 구조인가

**Ace 안이 명확하다. Master 안은 Grade 수를 유지하면서 문제를 이동시킨다.**

**Master 안의 구조:**
- D에 현행 C(판단여지 있는 경량) 편입
- 새 C = 경량 + 필요 역할 호출
- 결과: Grade가 여전히 A/B/C/D 4단계

**Ace 안의 구조:**
- C/D 통합 → "경량 Grade" 1개 (또는 D 단일로)
- B에 격상 트리거 박제: "파일 2개 이상 의존 변경·스키마 수정·hook 경계 변경"
- 결과: Grade A/B/D 3단계 (또는 A/B/Light)

**프레이밍 관점 판정:**

Ace 안은 **판단 기준을 Grade 수가 아니라 격상 트리거에 외재화**한다. "이 토픽은 D인가 C인가?"를 묻는 대신 "파일 2개 이상 의존 변경이 있는가?"를 묻는다. 후자가 훨씬 객관적이고 Nexus가 판단하기 쉽다.

Master 안은 문제를 이동시킨다: C/D 경계가 불명확하다 → C를 재정의 → 새 C와 D의 경계 불명확 문제 재발. 이동된 문제를 해결하지 않았다.

**Riki의 우려에 대한 추가 관점:** Riki는 C/D 통합이 구조 drift를 야기할 수 있다고 경고했다. 그런데 Ace 안은 통합 + 트리거 박제이므로, 트리거 기준이 drift 방어선이다. 트리거를 명확히 박제하면 Riki 우려는 해소된다. Ace 안에 Riki 트리거 기준을 인라인 박제하는 것이 최적 결합이다.

**결론: Ace 안 채택 + Riki 트리거 기준 인라인 박제.**

## 3. B vs 새 C 경계 — Jobs가 제안하는 단일 기준

**의사결정 필요 여부. 단일 기준.**

이유: Nexus 자동 판단에 가장 적합한 기준은 "토픽을 보는 순간 판단 가능"해야 한다. 규모·복잡도는 종종 들여봐야 알고, 결과가 나와봐야 알기도 한다. 반면 "이 토픽에 Master 또는 역할이 내려야 할 결정이 있는가"는 토픽 설명 한 줄로 판단 가능하다.

| 기준 후보 | Nexus 판단 시점 | 판단 용이성 | 오분류 비용 |
|---|---|---|---|
| 규모(≤5 파일) | 사전 추정 필요 | 낮음 (실착 잦음) | 중간 |
| 구조 복잡도 | 들여봐야 앎 | 낮음 | 낮음 |
| **의사결정 필요 여부** | **토픽 설명으로 즉시** | **높음** | **높음** |

"의사결정이 없다 = Dev 직행 경량 처리 (D)" / "의사결정이 있다 = 역할 투입 (B 이상)"

이 단일 기준이 B↔경량 Grade 경계를 구성한다. B는 의사결정이 있는 토픽의 하한이다.

**부수 조건:** 의사결정이 있는데 Size가 ≤5이면 B. Size가 6~10이면 B. 의사결정이 없으면 D(경량). A는 의사결정이 있고 불확실성이 높거나 다축 분석 필요한 것.

즉, Grade 계층은 이렇게 재정의된다:
- **D**: 의사결정 없음 + 실행만 (Dev 직행)
- **B**: 의사결정 있음 + 전제 조건 닫힘 (명확 결정건)
- **A**: 의사결정 있음 + 전제 조건 열림 또는 다축 분석 필요
- **S**: Master 명시. 오픈 탐색형.

C는 폐기한다. C가 담당했던 "경량 + 판단 여지"는 "의사결정 있음 + Size 작음"이므로 → B로 흡수. "경량 + 판단 여지 없음"은 → D.

## 4. S 로스터 최종 확인 — Jobs 발동 조건 + `/jobs-framing` 인라인 박제 동의 여부

**동의한다. 박제 형태는 아래와 같다.**

**Jobs 발동 조건 (S 로스터 인라인):**

```
S 기본 로스터:
- Jobs: /jobs-framing 명시 호출 시 발동 (자동 아님)
- Ace: 구조·흐름 판정
- Arki: 의존 분석·실행계획
- Riki: 실패 모드·전제 감사
- Edi: 산출물 박제

선택:
- Fin (재무 분석 필요 시)
- Dev (구현 진입 후)
- Vera (시각 설계 필요 시)
- Nova: 제외. (CLAUDE.md "optional unless explicitly promoted" 정책 유지 — S에서도 동일)
```

**이 박제의 의미:**

S에서 Jobs는 "기본 로스터에 있지만 자동 발동하지 않는 역할"이다. S 선언이 곧 `/jobs-framing` 자동 트리거가 아니다. Master 또는 Nexus가 명시 호출해야 한다. 이는 D-130 자동 트리거 폐기 원칙과 정합하고, S의 탐색적 성격과도 맞는다 — S 토픽이라도 framing이 필요 없는 경우가 있다 (이미 문제가 명확한 경우).

**Nova 제외에 대한 Jobs 입장 (R1에서 동의했지만 근거 명시):**

Nova를 S 기본 로스터에서 제외하는 것이 맞다. 이유:

1. **Nova의 가치는 불확실성의 증폭이 아니라 막힌 구조에서의 우회다.** S가 오픈 탐색형이라는 이유로 Nova를 기본 포함하면, Nova는 "탐색 역할"로 domesticated된다. Nova의 본질 — "구조적 교착 시 전복" — 을 희석한다.

2. **S에서 Nova가 필요한 상황은 Riki가 🔴 2개 이상 + 교착 발생한 경우다.** 이는 S 시작 시점이 아니라 진행 중 조건이다. 기본 로스터 포함 여부보다 발동 트리거가 중요하다.

3. **"선택 역할"로 남기되 발동 조건을 명문화하는 것이 더 명확하다:**
   > Nova는 S에서 선택 역할. 발동 조건: (1) Riki 🔴 2개 이상 + 미해소, (2) 역할 간 구조 교착. Master 명시 없이 Nexus가 조건 충족 판단 시 Nova 추천 가능 — 최종 발동은 Master 승인.
