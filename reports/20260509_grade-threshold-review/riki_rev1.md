### 🔴 R-1. 매트릭스 분류 오판이 역할 호출 비용과 결합하는 임계 실패

**근거:**
현재 D 기준은 `bug·fix·patch·log·오타·수정(단독)·deploy·rollback` 키워드 매칭이다. A 기준은 "기본값"이다. 매트릭스 도입 시 이 이분법을 "주제 유형" 다차원으로 확장하는데, 분류 입력값은 Master의 짧은 자연어 발화다.

**실패 시나리오:**
Master가 "API 설계 좀 바꿔" 발화 → 표면 키워드 없음 → Nexus가 "구조 변경형" 으로 분류 → A 등급 full 로스터 자동 호출 → 실제 의도는 파라미터 명 변경 1건(D급 충분) → Arki·Fin·Riki 모두 발언, Master 체감 오버킬 → 신뢰 저하 및 Grade 시스템 불신

역방향도 동일하게 위험: "전체 인증 흐름 설계" → 키워드 없음 → Nexus가 "경량 기술 결정"으로 판독 → C/D 직행 → Arki 없이 구현 시작 → 구조 결함이 뒤늦게 노출.

**파손 범위:** 신뢰도 낮은 분류가 모든 역할 호출 결정의 단일 게이트가 됨. 오분류 1건이 전체 세션 품질을 결정.

**완화 조건:**
- Nexus가 분류 판단을 발언 형태로 먼저 제시하고 Master가 묵인/수정하는 확인 게이트 유지 (1회, tool blocker 아님)
- 매트릭스 자체에 "불확실" 버킷 + 기본값 A 복귀 경로를 명시
- 분류 오판 사례를 evidence_index에 축적해 매트릭스 revision 트리거로 사용

### 🔴 R-2. C/D 통합 시 "Arki 없는 구조 결함 누적" 위험

**근거:**
C와 D의 현재 차이는 "Arki 검토 유무"다. Master가 제기한 문제는 Arki가 실제로 거의 안 나온다는 것이다. 그런데 이 관찰은 **Arki가 불필요해서 안 나온 것**인지, **호출 마찰이 높아서 안 나온 것**인지 구분되지 않는다.

**통합 시 실패 시나리오:**
C+D가 "Dev 직행"으로 통합 → 6~10건 규모의 기술 결정들이 모두 Arki 없이 처리 → 개별 결정은 작지만 누적 구조 drift 발생 → 3개월 후 시스템 일관성 감사 시 근거 없는 구현이 다수 발견 → 소급 비용 급증

**유지 시 실패 모드:**
C 존재하나 Arki 실제 호출율 0% 상태 유지 → dead rule → CLAUDE.md 문서와 운용 실제 간 drift → 신규 세션에서 CLAUDE.md를 신뢰하고 C 토픽에 Arki 호출했더니 "불필요" 판단 받는 혼선

**어느 쪽이 더 나쁜 실패인가:**
통합이 더 나쁘다. C 유지 + Arki 미호출은 비효율이지만 복구 가능하다. 통합 후 구조 결함 누적은 비가역적이다. 단, C 규정 중 "Arki 호출 트리거 조건"을 현재보다 명시적으로 좁히지 않으면 유지해도 문제가 반복된다.

**완화 조건:**
- 통합 선택 시: C급 토픽에서 구조적 의존성이 생기는 판단 기준(예: "2개 이상의 기존 파일을 수정하는 결정")을 명시하고 해당 조건 충족 시 Arki 자동 호출
- 유지 선택 시: C 트리거 조건을 "키워드 기반" → "결정 파급 범위 기반"으로 재정의

### 🟡 R-3. S 로스터에 Jobs+Nova 동시 추가 시 프레이밍 주도권 충돌

**근거:**
현재 S grade는 "Master 선두, Jobs framing 명시 호출 시 발동"이다. Nova는 "Riki 2+ critical 또는 구조적 교착 시 Master가 명시 호출"이다. 둘 다 명시 호출 조건이지만 S 기본 로스터에 포함되면 **"명시 호출 없이도 기본 참여"로 의미가 바뀐다.**

**Jobs 추가 리스크:**
Jobs가 기본 로스터에 있으면 S 토픽 시작 시 자동으로 framing phase가 열린다. S의 특성은 Master가 탐색 주체인 "오픈 탐색형"이다. Jobs가 framing을 선점하면 Master의 탐색 공간이 Jobs의 프레임 안으로 수렴 → S의 정의(Master 선두 오픈 탐색)와 충돌.

**Nova 추가 리스크:**
Nova가 기본 로스터에 있으면 S 전체 세션에서 Nova의 사변적 발언이 기본 포함 → 각 역할의 실용 분석과 사변 발언이 섞임 → Edi 종합 단계에서 Nova 발언의 가중치 처리가 모호해짐 → "Nova는 speculative"를 명시해도 S 기본 로스터면 Master가 Nova 발언을 실용 발언으로 오독할 위험.

**파손 범위:** S 토픽의 설계 의도(오픈 탐색) 훼손. "기본 로스터 = 기본 참여 = 기본 발언 권한"으로 인식되는 관성.

**완화 조건:**
- Jobs는 S 로스터에 포함하되 "framing phase = Master 명시 `/jobs-framing` 호출 시만" 조건을 로스터 정의 안에 인라인으로 박제
- Nova는 S 로스터 기본 포함 대신 "S 토픽 시작 시 Nexus가 Nova 포함 추천 여부를 1회 질문" 방식 유지

### 🟡 R-4. 매트릭스 자체가 Nexus 판단 대체재로 오용될 위험

**근거:**
Master의 목표는 "Nexus가 주제 유형을 보고 자동 결정"이다. 매트릭스 완성 후 Nexus는 매트릭스를 lookup table로 사용하게 된다. 그런데 실제 토픽은 단일 유형에 깔끔하게 맞지 않는다. "API 설계인데 보안이 핵심", "기능 구현인데 전략적 피벗 판단 필요" 같은 복합 유형이 실운용의 대다수다.

**실패 시나리오:**
매트릭스가 X축(구조변경/기능구현/전략결정/버그수정)×Y축(영향범위)로 정의됨 → Nexus가 토픽 발화를 보고 셀을 찍음 → 복합 유형 토픽은 경계 셀에 걸림 → Nexus가 더 낮은 Grade 쪽으로 판정(보수 편향) 또는 임의 선택 → 실제로는 A급 필요한 토픽이 C로 처리됨

더 위험한 실패: 매트릭스 존재 자체가 Nexus에게 "판단 책임을 매트릭스에 전가"하는 심리적 허가로 작동 → Nexus의 컨텍스트 의존 판단력 퇴화 → 매트릭스 외 케이스 대응 능력 감소.

**파손 범위:** 매트릭스 도입 이후 분류 정확도가 도입 이전보다 낮아질 수 있음. Master 개입 최소화가 오히려 오분류 감지 지연으로 이어짐.

**완화 조건:**
- 매트릭스는 "Nexus 판단 보조" 위치 유지. "Nexus 판단 대체" 금지를 CLAUDE.md 매트릭스 정의 섹션에 명시
- 매트릭스 룩업 결과와 Nexus 컨텍스트 판단이 다를 경우 Nexus가 후자를 우선하는 우선순위 명시
- 경계 케이스에서 Nexus가 Master에게 1회 확인하는 경로 보존

### 🟢 R-5. "Arki 선두 고정" 폐기 시 A/B 첫 발언 공백

**확인 수준이 낮아 🟢 분류.**

A/B에서 Arki 선두를 없애고 주제 유형별로 첫 발언자를 바꾸면 Fin이 선두인 경우(비용/자원 중심 토픽)에 구조 분석 없이 비용 이야기부터 시작하는 역전이 발생한다. Fin의 역할 정의는 "구조 설계 단계엔 방향성만"이다. 구조 없이 비용만 논의하면 근거 없는 숫자가 나온다.

**완화 조건:** 첫 발언자 자동화 시 "첫 발언자가 Arki가 아닌 경우 Arki를 2번째로 강제"하는 순서 제약 추가.
