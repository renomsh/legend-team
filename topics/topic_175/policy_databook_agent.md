## 1. 헤더 행 동적 탐지 정책

### 배경
실측 결과 팀 파일마다 헤더 행 위치가 다르다.

| 파일 | 헤더 행 | 비고 |
|---|---|---|
| 기교1팀 | row 22 | |
| 기교2팀 | row 23 | |
| 기교3팀 | row 21 | |
| FS1팀 (xlsb) | 미확인 | `'26년 databook(취합)'` 시트 존재 확인 |
| FS2팀 | row 21 | |
| FS3GS팀 | row 24 | 다른 팀보다 3행 늦음 |
| 취합본(main) | row 3 | 시트명 `'26년 Databook(취합)'` (대문자 D) |
| 전주 취합본 | row 3 | 컬럼 수 53열 (현재 58열보다 5열 적음) |

### 정책
- 셀 고정 지정 **절대 금지**
- 시트 첫 50행 스캔, 핵심 헤더 텍스트 매칭으로 헤더 행 자동 탐지
- 핵심 매칭 키: `"고유번호"` 단독 또는 `"기업명"` + `"기업코드"` + `"26년 담당팀"` 중 3개 이상
- 시트명 매칭 패턴: `"취합"` 부분 일치 (대소문자 무시)
- 데이터 시작 행 = 헤더 행 + 1
- 데이터 종료 행 = 기업코드/기업명 모두 비어있는 첫 행 직전

### 경고 게이트 (2단계)
| 단계 | 조건 | 동작 |
|---|---|---|
| 🟡 WARN | 헤더 행이 전주 위치 ±2행 초과 이동 | 운영자 확인 요구(Y/N) |
| 🟡 WARN | 새 컬럼 발견 (canonical 미정의) | 매핑 무시 + 로그 + 확인 요구 |
| 🟡 WARN | 컬럼 수가 전주와 다름 | 마감월 추가 의심 → 헤더 텍스트 재매핑 |
| 🔴 ABORT | 핵심 컬럼 4종 매칭 실패 | 즉시 중단 |
| 🔴 ABORT | 헤더 행 50행 스캔 실패 | 즉시 중단 |
| 🔴 ABORT | 데이터 행 중간 빈 행 발견 | 즉시 중단 + 위치 보고 |

## 2. PK 자연키 정의

### 배경
- 같은 (기업코드 + 사업유형) 조합이 1,174건 중복
- 97%(1,140건)가 (주), (유) 등 괄호 표기 차이 → **각각 별도 거래** (병합 대상 아님)
- 영업기회코드는 FS3/GS팀(97%)만 사용, 다른 팀(0~8%) → 보조 키 부적합

### 정책
**자연키 = `기업코드 + 26년 사업유형 + 기업명(원본 그대로)`**

- 기업명 정규화 **금지**: (주), (유), (GKL) 등 괄호 표기는 별도 거래 식별자
- 자연키 → 시스템 발급 PK 매핑은 `work/pk_lookup.json`에 누적 보관
- 첫 등장 시 신규 PK 발급 (예: `LGT-000001`)
- 재실행 시 lookup 우선 조회, 미스 시에만 신규 발급 → 멱등성 보장

### 1차 회차 운영 (Phase 2.1~2.3)
- 검토 큐 4분류:
  - **A. 동일(미세차이) 16건** — 운영자 spot check 후 병합 가능
  - **B. 이름변형(괄호) 1,140건** — 자동 별도 PK (병합 X)
  - **C. 연도분기 2건** — 자동 별도 PK (시간축 분리)
  - **D. 실제별건(담당 다름) 16건** — 자동 별도 PK
- 1차 회차 운영자 검토 부담: **A 16건만**

## 3. (사용안함) 행 필터 정책

### 배경
취합본에 `(사용안함)` 표기 행 11건 (전부 FS3/GS팀)
- 25/26년 매출 0인 행 7건 = 비활성
- 25/26년 매출 있는 행 4건 = 잔여 매출 처리 중

### 정책 (Master 확정 2026-05-06)
- **25년 매출 마감 = 0 AND 26년 예상매출합계 = 0** → 취합 제외
- 위 조건 미충족 시 (어느 한쪽이라도 매출 있음) → 취합 포함
- 필터링 시점: normalize 단계 (정규화 직후)
- 필터링 대상은 `work/filtered/excluded_unused_{date}.csv`에 박제 (제거 X, 보관)
- schema.json 외재화: `filterRules.excludeUnused: { nameContains: "(사용안함)", revenueZeroBoth: true }`

## 4. 컬럼 수 변동 대응 정책

### 배경
- 전주(4/9): 53열 (3월 미마감)
- 현재(5/7): 58열 (3월 마감 추가 → +5열)
- 매월 마감 시 "X월 매출", "매출변동 사유" 컬럼 추가 → 4월 이후 컬럼 위치 밀림

### 정책
- closedMonths schema 외재화: `schema/closed_months.json` = `[1, 2, 3]`
- 매월 마감 추가 시 운영자가 정수 1개 추가 (스크립트 수정 불요)
- 헤더 텍스트 교차 검증 필수: `closedMonths` 값에 따라 예상되는 헤더 텍스트와 실제 헤더 매칭
- 불일치 시 ABORT
- 전주 비교 시 **반드시 헤더 텍스트 기반 매핑** (열 번호 매핑 금지)

## 5. 개인 파일 처리 정책

### 배경
- 개인 파일(예: 박정규_완료.xlsm)은 팀 전체 데이터 1,052행 포함
- 영업대표 본인 행만 편집, 타인 행은 스냅샷으로 보존
- "변경 없음" 텍스트 파일은 미제출 표시

### 정책
- 개인 파일 정규화 시 **G열(26년 영업대표 = 본인 이름)** 기준 필터링하여 본인 행만 추출
- 미제출자 행은 전주 팀 완료 파일에서 가져옴 ("팀 중에 있는 사람들만 전 주와 수정 반영, 없는 사람 유지")
- 팀 완료 파일은 SOT — 모든 사람(제출자+미제출자) 행 통합 결과
- 개인 파일 안의 타인 행은 무시 (팀 완료 파일과 SOT 충돌 시 팀 완료 파일 우선)

## 6. F열 팀 분리 정책

### 배경
- FS3+GS는 한 파일로 입력, F열(26년 담당팀) 값으로 분리
- F열 표기 실측: `"기업교육1팀"`, `"FS1팀"`, `"FS3팀"`, `"GS팀"` 등 명시적 분리됨

### 정책
- F열 빈 값 또는 unknown 행 발견 시 ABORT (자동 분류 금지)
- F열 고유값을 Step 0에서 출력 → 운영자 육안 확인 게이트
- teams.json 외재화: `splitValues: ["기업교육1팀","기업교육2팀","기업교육3팀","FS1팀","FS2팀","FS3팀","GS팀"]`
- 신규 팀 추가 시 schema 갱신만으로 처리

## 7. 사업취소 처리 정책

### 배경

- 사용안함 행은 §3 정책으로 별도 처리
